# 10. Installing This as a PWA — What That Means and How It Would Work

This is the last document in the series. It answers directly: once everything
above is finished, how does an operator (or a device technician) actually end
up with this application running full-screen on the Jetson the way the
legacy PyQt5 app used to, just by the device powering on?

**Everything in this document describes the intended mechanism. None of it
has been tested end-to-end on a device yet** — see `todos.md`. It's written
now so the rollout has a concrete plan to test against, not as a record of
something already verified.

## What "installing as a PWA" actually means here

A PWA is not a separate build artifact you copy onto the device — it's the
same web app (`eye_compass_fe`), served over HTTP(S), that a browser is able
to treat as an installable, standalone application because it has two things:

1. **A web app manifest** — already configured in `vite.config.js` via
   `vite-plugin-pwa` (`name`, `display: 'standalone'`, `theme_color`, an
   icon). This tells the browser the app can be "installed" and should run
   without its own address bar/toolbar chrome when it is.
2. **A service worker** — also generated by `vite-plugin-pwa`, which lets the
   browser cache the app's assets so it can load instantly (and, to a limited
   extent, offline) rather than re-fetching everything from the dev/production
   server on every launch.

"Installing" it, concretely, means either:
- A person visiting the frontend's URL in Chromium/Chrome and using the
  browser's own "Install app" prompt (or `chrome://apps` → "Install"), which
  creates a desktop/launcher entry that opens the app in its own
  chrome-less window, or
- On a kiosk device, skipping the manual install step entirely and instead
  launching Chromium directly against the frontend's URL with kiosk flags
  (see below) — for a single-purpose device like this, that is simpler and
  more reliable than relying on a one-time manual "Install" click surviving
  reboots.

## Prerequisite: serve a real production build, not the dev server

Everything run so far has used Vite's **dev server** (`npm run dev`, live
inside the `frontend` Docker container). A dev server is not what a kiosk
device should point at long-term: it recompiles on file changes, has none of
production's asset minification/caching, and its own PWA-eligibility can
behave differently than a real build's. The production path already exists
but has not yet been the one actually run:
- `npm run build` (or the `Dockerfile`/`nginx.conf` already present in
  `eye_compass_fe/`) produces the real static bundle plus the generated
  manifest/service worker.
- `nginx.conf` already has the `/api/`/`/ws/` proxy blocks mirroring the dev
  server's, and the SPA fallback (`try_files ... /index.html`) so deep links
  survive a refresh in kiosk mode.

## Bringing up a device, end to end

Tying together `5 - infrastructure_and_deployment.md`'s hybrid split:

1. **Database + frontend**: `sudo docker compose up -d` from the folder
   containing the root `docker-compose.yml` (switched to the production
   frontend build/Nginx target once that path is actually exercised — see
   `todos.md`).
2. **Backend**: the systemd unit (`eye-compass-backend.service`) enabled so
   it starts on boot and restarts on failure, pointed at the virtualenv with
   both the web and ML stacks (`/home/nvidia/.virtualenvs/eye_compass`).
3. **Kiosk browser autostart**: the device's desktop session needs to launch
   a browser, full-screen, pointed at the frontend, with no further
   interaction. The general shape (not yet set up or tested on this device):
   - A `systemd` **user** service, or an XDG autostart `.desktop` entry, that
     runs on graphical login/boot.
   - Launches Chromium with kiosk flags, e.g.
     `chromium-browser --kiosk --app=http://localhost:5173 --noerrdialogs --disable-session-crashed-bubble`
     — `--app=` (rather than plain `--kiosk <url>`) is what makes Chromium
     treat it as an installed-app-style window (no tabs, no address bar)
     rather than merely a full-screen normal browser window.
   - The device should already be logged into a graphical session
     automatically (auto-login), since there is no operator available to type
     a password at boot on an unattended kiosk.

## What's genuinely still open here

- Whether to rely on Chromium's own "installed PWA" mechanism (`--app=`) or a
  plain `--kiosk <url>` full-screen browser window — both achieve a
  chrome-less full-screen view, but behave slightly differently around things
  like the service worker's install prompt and update flow. Worth deciding
  deliberately, not defaulting to whichever is easiest to script.
- The manifest's icon and theme colors are still placeholders (see
  `3 - frontend_setup_walkthrough.md`) — worth finalizing to match legacy's
  actual "Compass Eye" branding before this is what a technician sees appear
  on a real device.
- None of this has been tested against an actual reboot cycle — auto-login,
  service startup ordering (the browser launching before the frontend
  container/backend are actually ready to answer requests is a real failure
  mode worth explicitly handling, e.g. a retry/splash rather than a blank
  error page), and recovery after a crash.

See `todos.md` for this tracked as an explicit open item.
